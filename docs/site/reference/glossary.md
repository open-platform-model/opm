This page defines every Open Platform Model (OPM) term and every CUE term the documentation uses, once each, for a reader who runs Kubernetes and has never used OPM or CUE. The rows follow the product: the model, rendering, identity and versions, deploying, diagnostics and publishing, then CUE terms last.

| Term | Definition |
| --- | --- |
| Module | `#Module`: the published description of an application, made of components, a configuration schema (`#config`) and example values (`debugValues`). It is versioned and distributed as a CUE module through an OCI registry. |
| Component | `#Component`: one deployable unit inside a module, usually one workload, built by attaching resources, traits and blueprints. Its `spec` is the unification of the `spec` of everything it attaches. |
| Primitive | The collective name for resources, traits and blueprints: the building blocks a catalog publishes and a module attaches. Each is keyed by a contract and carries an `apiVersion`; transformers are not primitives. |
| Resource | `#Resource`: a primitive for something that must exist at runtime, such as a container, a volume, a ConfigMap or a Secret. It is not a Kubernetes kind; which objects it becomes depends on the transformers that match it. |
| Trait | `#Trait`: a primitive that changes how a component's resources behave, such as scaling, exposure or a security context. Its `appliesTo` field lists the resources it is meant for; the schema does not check that a component attaching the trait carries one of them. |
| Optional trait | A trait whose `optional` field resolves to `true`: when no transformer that matched the component handles it, the render continues with a warning, and when `optional` resolves to `false` the render fails. The catalog states the posture as a default, and a component may override it where it attaches the trait. |
| Blueprint | `#Blueprint`: a primitive that composes resources and traits into one attachable unit. A workload blueprint, such as `stateless-workload` or `stateful-workload`, also answers the component's matching label. Choosing a blueprint is the nearest thing in OPM to choosing a Deployment or a StatefulSet. |
| Wrapper | A ready-made `#Component` fragment a catalog ships for one primitive, such as `#StatelessWorkload` (a blueprint), `#Expose` (a trait) or `#ConfigMaps` (a resource). A module embeds wrappers into its component instead of attaching the primitive by its contract key. |
| Module configuration (`#config`) | The schema, with defaults, that a deployer's values must satisfy, written by the module author and meant to stay expressible in OpenAPI v3, which nothing checks. A key it does not declare fails with `field not allowed` in a `-f` file, in a module's `debugValues` under the `opm module` commands, and in a `ModuleInstance`'s `spec.values`. |
| `debugValues` | Example values a module ships so it can be built without an instance file. `opm module build`, `opm module apply` and `opm module vet` use them when no `-f` is given, and `-f` replaces them entirely. |
| `initValues` | An optional `#Module` field holding the values a new instance package starts from; `opm instance init` writes it into the package's `values.cue`, even when it is not fully concrete. When a module has no `initValues`, `opm instance init` falls back to `debugValues` only if they are fully concrete once defaults apply, and otherwise writes an empty struct. |
| Values | The concrete configuration a deployer supplies for one instance: the `values` field of an instance, `values.cue` beside an instance file, files passed with `-f`, or `spec.values` on a `ModuleInstance` resource. Several sources are unified, so two different values for one field conflict. A misspelled key in `values.cue` or the `values` field is not reported when the CLI renders the package for an instance it owns, or when the operator renders a `ModulePackage`. |
| Layering contract | The rule for which layer may write which kind of value onto a component field: resources and traits give bounds only, a blueprint at most one default per field, the module author defaults only inside `#config`, and a transformer falls back only when a field is absent. Nothing checks it, because CUE cannot tell which layer wrote a value. |
| Instance | `#ModuleInstance`: one deployed copy of a module, binding it to values, a name and a namespace. Its identity (`metadata.uuid`) derives from the module's registry path, the name and the namespace, so it survives module version and major upgrades. |
| Synthetic instance | An instance the CLI builds around a module so `opm module build`, `opm module apply` and `opm module vet` can render without an instance file. It is named after the module with `_` replaced by `-` and `-debug` appended, in namespace `default`, unless `--name`, or `--namespace` or `OPM_NAMESPACE`, is given. |
| `resourceName` | `metadata.resourceName` on a component: the name its rendered objects get. It defaults to `<instance>-<component>` and a component may override it with a DNS subdomain name that every attached primitive's name rule accepts; a stateful workload's must be a DNS label. |
| `#names` | The names a component computes once from its `resourceName` and its instance: `resourceName` and the DNS forms `dns.short`, `dns.local` (`<resourceName>.<namespace>`) and `dns.fqdn` (`<resourceName>.<namespace>.svc.<clusterDomain>`). Other components read them through `#ctx.components`. |
| Transformer | `#ComponentTransformer`: a function a catalog ships that turns a matched component into Kubernetes objects. It declares the labels, resources and traits a component must carry to match (`requiredLabels`, `requiredResources`, `requiredTraits`), runs at render time and applies nothing. |
| Matching | How the render pairs components with transformers. A transformer matches a component when every `requiredLabels` entry appears in the component's `matchLabels` with the same value, every required resource and trait contract is attached, and the attached values unify with the transformer's required ones; every transformer that matches a component runs for it. |
| Verdict | The result of matching one transformer against one component (`CandidateVerdict`): matched or not, plus the required labels the component lacked or carried with a different value. A component that no transformer matched is reported with the verdict of every candidate, meaning every transformer that requires or uses a resource or trait it carries, in the [Unmatched components](/docs/diagnostics/unmatched-components/) error. |
| `matchLabels` | The labels a component uses for matching, collected from the primitives it attaches, such as the abstraction catalog's `core.opmodel.dev/workload-type`. A transformer's `requiredLabels` are compared with them at render time, never on the cluster, and `metadata.labels` are never read for matching. |
| Workload type | The matching label `core.opmodel.dev/workload-type`, with the values `stateless`, `stateful`, `daemon`, `task` and `scheduled-task`. The container resource requires it, and a workload blueprint answers it. The value selects the transformer that emits a Deployment, StatefulSet, DaemonSet, Job or CronJob. |
| Contract | The key a module demands and a catalog defines, written `<catalog registry path>/<kind>/<name>@<apiVersion>`, for example `opmodel.dev/catalogs/opm/resources/container@v1beta1`. A resource, trait or blueprint is identified by its contract, and a transformer names the contracts it requires. The key carries the contract level, not the catalog release. |
| Contract level (`apiVersion`) | A primitive's own version on the Kubernetes ladder (`v1alpha1`, `v1beta1`, `v1`), set by its author and never moved by a catalog release; a breaking change to the primitive must move it. The additive-only promise binds beta and GA levels and not alpha, and transformers carry no `apiVersion`. |
| Additive-only promise | The rule that a contract at a beta or GA level only gains fields, so a breaking change needs a new `apiVersion`; alpha levels promise nothing. `opm catalog publish` refuses a beta or GA resource, trait or blueprint that breaks against the newest earlier build in the same major that carried it, and skips the check for development builds and prerelease versions. |
| Fulfilment | `fulfilment` on a resource or trait. `catalog` (the default) means the declaring catalog ships the transformer. `provider` means the declaring catalog deliberately ships none, and exactly one provider on the platform must supply it (see Provider). |
| Provider | An enabled registry entry on a platform, a catalog module path with its major such as `opmodel.dev/catalogs/k8up@v2`, whose transformers require a provider-fulfilled contract. A platform carries at most one provider per contract, counted by entry: two transformers in one entry are one provider, and two majors of one catalog are two. |
| Catalog | `#Catalog`: a versioned CUE module that lists the resources, traits and blueprints it defines and the transformers it implements. A platform enables catalogs to decide what a render can produce. |
| Abstraction catalog | `opmodel.dev/catalogs/opm@v4`: the first-party catalog of abstractions (container, volumes, workload blueprints, traits) that modules start from. |
| Raw Kubernetes catalog | `opmodel.dev/catalogs/k8s@v1`: the first-party catalog that carries native Kubernetes kinds through as written, with no traits and no blueprints. It is the escape hatch when no abstraction fits. Most of its resources render one object each; the `Objects` resource carries several arbitrary objects, custom resources included, in one component. |
| Platform | `#Platform`: the set of catalogs a render may use, written as a CUE module that imports each catalog and lists it in `#registry` under its module path. On a cluster it is the `Platform` resource, a cluster-scoped singleton that must be named `cluster`, from whose `spec.registry` and active `TransformerRegistration` claims the operator generates that module. |
| Platform module | The CUE module that holds a platform: its `cue.mod/module.cue` pins each catalog build and its `platform.cue` imports the catalogs, so the pins decide which builds a render uses. The CLI also generates one from the cluster's `Platform` resource or from the render's own pins, and `opm platform pull` writes the cluster's to a directory. |
| Subscription | An entry in the `Platform` resource's `spec.registry`: a catalog module path with a pinned `version` that a platform admin enables. The other way a catalog reaches the platform is an active `TransformerRegistration` claim. |
| Contract inventory | `#contracts` on a platform, derived from its enabled catalogs: which contracts they define and which entry defines each, which transformers require each, which entries provide each provider-fulfilled contract (`providedBy`), the reports `unfulfilled`, `overSubscribed`, `comparable` and `collisions`, and the flags `fulfilled`, `routable` and `discriminated`. `opm platform check` prints it. |
| Kernel | The Go library (`library/opm/kernel`) that acquires modules, catalogs, instances and platforms, validates values and renders. The CLI and the operator both embed it. It applies nothing to a cluster. |
| Render | Turning an instance into Kubernetes objects against a platform, in one CUE build. `opm instance build`, `opm instance vet` and `opm instance diff` render, as do `opm module build` and `opm module vet`, and the first half of each apply command and of an operator reconcile. |
| Module path | The complete CUE module path of a module or catalog, including its major version, such as `opmodel.dev/modules/web_app@v1`. The same string appears in `cue.mod/module.cue`, in import statements and as the registry coordinate, and core types it as `#ModulePathType`. |
| Registry path | The module path without its `@vN` major, such as `opmodel.dev/modules/web_app`. It is the OCI repository that holds the artifact's versions, core computes it through `#ArtifactRef`, and it is one of the three inputs to an instance's identity. |
| Major | The `@vN` suffix of a module path. A new major marks a breaking release. `opm module publish` refuses a version whose major differs from the path's, so a `@v1` module publishes only `1.x.y` versions. |
| Version | An artifact's SemVer release, `metadata.version` on a module or catalog, set in its identity package. A module's version is not part of its instance identity, so upgrading it keeps the same instance. |
| Catalog version | `metadata.catalogVersion` on a resource, trait, blueprint or transformer: the release of the catalog that shipped the definition, stamped by the catalog. For resources, traits and blueprints it is provenance only; for a transformer it is part of the key (see FQN). |
| FQN | `metadata.fqn`, the full key of an artifact or catalog member. A module's or catalog's FQN is its module path, a resource's, trait's or blueprint's is its contract, and a transformer's ends in the catalog release, such as `opmodel.dev/catalogs/opm/transformers/deployment-transformer@4.4.5`. An instance's FQN is `<registry path>:<name>:<namespace>`. |
| Identity package | The `identity/identity.cue` file that every module and catalog commits, holding `ModulePath` and `Version`. `opm module vet` and the publish commands check it against core's `#IdentityPackage` and refuse a file that does not conform. |
| Instance UUID | `metadata.uuid` on an instance: a UUID v5 (SHA1) of `<module registry path>:<name>:<namespace>`. Because it uses the registry path, it does not change when the module's version or major changes. Every rendered object carries it in the `module-instance.opmodel.dev/uuid` label, which pruning compares. |
| Version skew | An instance whose `cue.mod/module.cue` requires a newer build of core or of a catalog than the platform pins. The render uses the platform's build and warns, or stops before evaluation under a refuse policy: the `Platform` resource's `spec.skewPolicy` (`Warn` or `Refuse`) for the cluster's platform, in the CLI and the operator alike, and `skewPolicy` in `~/.opm/config.cue` for a `--platform` directory. See [Version skew](/docs/diagnostics/version-skew/). |
| Apply | Sending rendered objects to the cluster with server-side apply and recording them in the instance's inventory. `opm instance apply` and `opm module apply` do this from the CLI, and the operator does it on each reconcile. |
| Inventory | The list of objects an instance deployed, kept in `status.inventory` on its `ModuleInstance` resource. Pruning and deletion work from this list. A `ModulePackage` keeps its own `status.inventory` and does not create a `ModuleInstance`. |
| Prune | Deleting objects that a new render no longer emits, and on deletion removing everything the inventory lists. `opm instance apply` prunes unless `--no-prune` is given; the operator prunes only when the resource's `spec.prune` is `true`, and the CLI never writes `spec.prune`. |
| Owner | `spec.owner` on a `ModuleInstance`: `cli` or `operator`, where an absent or empty value means `operator`. The CLI writes `cli` when it creates the resource and never rewrites an existing owner. The operator renders, applies and prunes only the instances it owns; against those, the CLI edits only `spec.module` and `spec.values`. |
| Operator | The `opm-operator`, a Kubernetes controller that reconciles `ModuleInstance`, `ModulePackage`, `Platform` and `TransformerRegistration` resources and fetches published modules from the registry. `opm operator install` installs it. |
| `ModuleInstance` | The namespaced custom resource (group `opmodel.dev`, version `v1alpha1`, short name `mi`) that records an instance on the cluster. Its spec includes `module` (`path`, `version`), `values`, `owner` and `prune`, and its status holds the inventory. |
| `ModulePackage` | The namespaced custom resource (short name `mpkg`) that renders an `instance.cue` package from a Flux source artifact (`spec.sourceRef`) at `spec.path`. It tracks its own objects in `status.inventory`. |
| `TransformerRegistration` | The cluster-scoped custom resource (short name `treg`) that a provider module ships as a claim that its catalog implements provider-fulfilled contracts. Its spec holds `catalog`, `version`, `provides` and `providerRef`; once the operator accepts the claim and the provider's `ModuleInstance` reports Ready, the claim stays active until deleted and its catalog joins the platform the operator generates. |
| Colliding contract | A contract key that the catalogs of more than one enabled registry entry list, usually two majors of one catalog enabled together, which OPM does not support. The render fails with `ContractCollisionsError`, listed first among its causes, `opm platform check` lists the key under `colliding contracts`, and the operator sets the `Platform` Ready condition to False with reason `ContractCollisions`. See [Colliding contracts](/docs/diagnostics/colliding-contracts/). |
| Unresolved demand | A resource, or a trait whose `optional` is `false`, that a component carries and that no transformer matching that component handles. The render fails with `UnresolvedDemandsError`; with `--skip-unprovided` the CLI instead skips, with a warning, a provider-fulfilled contract that nothing on the platform provides, and a skipped resource leaves out its whole component. See [Unresolved demands](/docs/diagnostics/unresolved-demands/). |
| Unprovided contract | A provider-fulfilled contract that a component demands and that no enabled registry entry provides, so `#contracts.providedBy` has no key for it. It is an unresolved demand, and `--skip-unprovided` skips it with a warning. See [Unprovided contracts](/docs/diagnostics/unprovided-contracts/). |
| Unmatched component | A component that no transformer matched, so nothing would be rendered for it. The render fails with `UnmatchedComponentsError`, which lists each candidate transformer and, for a label mismatch, the required labels the component lacked. See [Unmatched components](/docs/diagnostics/unmatched-components/). |
| Oversubscribed contract | A provider-fulfilled contract that more than one enabled registry entry provides, so the platform has no single answer for who renders it. The render fails with `OverSubscribedContractsError`, and `opm platform check` prints the registry keys after `provided by`. See [Oversubscribed contracts](/docs/diagnostics/oversubscribed-contracts/). |
| Identity mismatch | A module fetched from the registry whose declared path or version differs from the coordinate it was fetched by. The kernel returns `IdentityError` naming both values, and the module is not used. See [Identity mismatch](/docs/diagnostics/identity-mismatch/). |
| Transform error | A transformer that matched a component but failed to produce concrete output for it. The kernel returns `TransformError` naming the component and the transformer and wrapping the CUE error that caused it. See [Transform failed](/docs/diagnostics/transform-failed/). |
| Registry mapping | The rule that sends a module path prefix to an OCI registry, such as `opmodel.dev=ghcr.io/open-platform-model`. The `cue` tool reads it from `CUE_REGISTRY`; `opm` takes it from `--registry`, then `OPM_REGISTRY`, then `registry` in `~/.opm/config.cue`, and falls back to `CUE_REGISTRY`. |
| Module template | A published module under `opmodel.dev/templates` (`minimal`, `standard` or `advanced`) that `opm module init` copies and gives the new module's path and version to start a new module; `--from` starts from any other published module. `opm module template list` prints the official set. |
| Publish gate | A core definition that `opm module publish` or `opm catalog publish` unifies an artifact against before it pushes: `#IdentityPackage` for both, and `#TraitOptionalGate` and `#CatalogMemberFQNGate` for catalogs. A failed gate refuses the publish and nothing is pushed. See [Publish refusals](/docs/diagnostics/publish-refusals/). |
| CUE | The configuration language OPM modules, catalogs and platforms are written in. CUE checks data against schemas and evaluates it by unification, so a value is valid when it satisfies every constraint written for it. |
| CUE module | A directory tree rooted at a `cue.mod/module.cue` file, which names the module path (`module: "opmodel.dev/examples@v1"`) and pins each dependency under `deps`. `cue mod init` creates the file and `cue mod tidy` fills in `deps`. |
| Package | The CUE files in one directory that share a `package` clause; CUE evaluates them together as one value. An instance's `instance.cue` and `values.cue` both declare `package podinfo` and form a single package. |
| Import | An `import` of another CUE package by its path, such as `"opmodel.dev/core@v2"`, optionally with an alias (`core "opmodel.dev/core@v2"`). An instance imports the module it deploys this way, a platform module imports its catalogs, and every imported module is pinned in `cue.mod/module.cue`. |
| Definition | A CUE schema whose field name starts with `#`, such as `#Module`. Definitions are closed, so they reject fields they do not declare, and `cue export` leaves them out of the data it emits. |
| Unification | CUE's one way of combining values, written `&`: the result satisfies both sides, and the order does not matter. Two different concrete values for one field cannot be combined, and CUE reports a conflict; there is no override order. |
| Conflict | The error CUE reports when unification cannot combine two values, printed as `conflicting values 4 and 3`. A concrete value written against a schema of another type conflicts the same way, for example `1` against `string`. |
| Concrete value | A value with no remaining choice, such as `3`, `"nginx"` or `true`. A type such as `int` is not concrete, and rendering needs every output field to be concrete. |
| Incomplete value | A value that is still a constraint or an unresolved choice, such as `int`. `cue export` reports it as `incomplete value int` when a concrete value is needed, for example for a field no layer has set. |
| Required field | A field declared with `!`, such as `modulePath!: #ModulePathType` in the `#Module` metadata. It must receive a value before the result is complete; otherwise `cue export` reports `field is required but not present`. |
| Optional field | A field declared with `?`, such as `description?: string` in the `#Module` metadata. It may be left out, and an optional field that nothing sets does not appear in the output. |
| Default | A disjunction branch marked with `*`, such as `replicas: int & >=1 \| *1` in the `web_app` example module. CUE uses it when nothing else sets the field. A field carries one default: two different defaults unified together cancel out and leave an incomplete value. |
| Disjunction | A choice between values, written with a vertical bar, such as `serviceType: "ClusterIP" \| "NodePort" \| "LoadBalancer" \| *"ClusterIP"` in the `web_app` example module. A value satisfies a disjunction when it matches one of the branches. |
| Closed struct | A struct that refuses fields it does not declare and reports `field not allowed`. Every definition is closed, so `#Module` refuses a misspelled top-level field such as `initValuez`; a plain struct that is not a definition accepts extra fields. |
| Hidden field | A field whose name starts with `_`, such as `_nameFits` in `#Component`. CUE does not emit it, and only files in the same package can refer to it. |
| Embedding | Writing a definition as a bare line inside a struct or at the top of a file, as in `core.#ModuleInstance` in an instance file, so the enclosing value takes on that definition's shape and its constraints. This is not the `@embed` attribute that loads files into CUE. |
| Pattern constraint | A rule applied to every field whose name matches, written `[Name=string]: …` with an optional alias for the matched name. `#components` in `#Module` uses `[Id=#NameType]: #Component & {…}` so each component entry is checked as a `#Component`. |
