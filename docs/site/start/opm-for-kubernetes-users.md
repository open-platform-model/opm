This page lists each Open Platform Model (OPM) term a Kubernetes or Helm user meets, next to the closest idea they already know and the point where the comparison stops holding. The rows follow the product: what a module is made of, what supplies rendering, identity, then deploying and the operator's resources. Each term's definition is in the [Glossary](/docs/reference/glossary/).

| OPM term | Closest Kubernetes or Helm idea | Where the comparison stops |
| --- | --- | --- |
| Module | A Helm chart. | A module has no templates and names no Kubernetes kinds. It is a CUE module, published to an OCI registry under a module path that ends in its major version, such as `opmodel.dev/modules/web_app@v1`. Its `metadata.name` is snake_case and must equal the path's last segment. |
| Module configuration (`#config`) | A chart's `values.schema.json`, together with the defaults in `values.yaml`. | The schema and its defaults are one CUE definition, with each default marked `*`. Values from a `-f` file, from `debugValues` and from a `ModuleInstance` resource's `spec.values` are unified with it, and an unknown setting is refused with `field not allowed`. Values written inside the instance package are not checked for unknown settings: a misspelled key there is ignored without an error. |
| `debugValues` | The values a chart author passes to `helm template` while developing the chart. | The CLI uses them only when it builds a module directory with no instance file: `opm module build`, `opm module apply` and `opm module vet`. Passing `-f` replaces them. They never reach an instance you write. |
| Values | `helm install -f values.yaml` and `--set`. | Values are unified, not merged. A later file cannot override an earlier one: two different values for one setting conflict, and the render fails. The whole instance package is loaded, so a `values.cue` beside the instance file always applies, and `-f` adds to it. |
| Component | One workload and the objects around it, such as a Deployment with its Service and HorizontalPodAutoscaler. | A component names no kinds. The platform's transformers decide which objects it becomes. Its objects are named `<instance>-<component>` by default, and `metadata.resourceName` overrides the name. |
| Blueprint | Choosing the workload controller: Deployment, StatefulSet, DaemonSet, Job or CronJob. | A blueprint renders nothing itself. It bundles resources and traits and sets the `core.opmodel.dev/workload-type` matching label, which selects the transformer. `opmodel.dev/catalogs/opm@v4` has five: `stateless-workload`, `stateful-workload`, `daemon-workload`, `task-workload` and `scheduled-task-workload`. |
| Resource | An API resource type, such as a container spec, a volume, a ConfigMap or a Secret. | An OPM resource is an abstract noun, not a Kubernetes kind. The `container` resource becomes a Deployment, StatefulSet, DaemonSet, Job or CronJob, depending on the component's `core.opmodel.dev/workload-type` label (`stateless`, `stateful`, `daemon`, `task` or `scheduled-task`), which a workload blueprint usually sets. Native Kubernetes objects the abstractions do not cover go in the `objects` resource (`opmodel.dev/catalogs/opm/resources/v1alpha1`), which renders them as written. |
| Trait | The settings and add-on objects you attach to a workload: a HorizontalPodAutoscaler, a PodDisruptionBudget, a Service, a security context. | A trait lists the resources it applies to in `appliesTo`, but nothing checks it: CUE accepts a trait on any component. A trait can make a transformer emit an object of its own, as the `expose` trait yields a Service. Its `optional` setting decides whether a trait no transformer handles fails the render or only warns. |
| `matchLabels` | A label selector. | Matching happens at render time, never on the cluster. A transformer's `requiredLabels` is compared with the component's `matchLabels`, which come only from the parts the component attaches. Core does not write `matchLabels` onto objects. The catalog's wrappers also set `core.opmodel.dev/workload-type` in the component's `metadata.labels`, so rendered objects carry that label anyway. |
| Transformer | One template file in a chart that emits one kind. | Transformers live in catalogs, not in the module, and matching chooses them. A transformer's `#transform` is a CUE definition evaluated at render, not a text template. One component can match several transformers, and every match runs. |
| Catalog | A library chart combined with an API group's CRD bundle. | A catalog is a versioned CUE module. It lists the resources, traits and blueprints it defines and the transformers it implements. It installs nothing on the cluster: a platform imports it. |
| Contract and `apiVersion` | Kubernetes API versions (`v1alpha1`, `v1beta1`, `v1`) on a group, version and kind. | A contract is keyed `<path>/<name>@<apiVersion>`, such as `opmodel.dev/catalogs/opm/resources/container@v1beta1`. At beta and GA a contract only gains fields; at alpha it promises nothing. The catalog's release version is recorded separately, as `catalogVersion`, and is not part of the key. |
| Platform | The set of APIs and controllers a cluster offers, as API discovery shows it. | A platform is a CUE module that imports its catalogs and pins each one's version in its own `cue.mod/module.cue`. On a cluster it is the `Platform` resource, cluster-scoped and named `cluster`. The CLI renders against the `--platform` directory, else the cluster's `Platform` (for the instance commands and `opm module apply`), else a platform generated from the render's own pins. It prints a `platform:` line that names the one it used. |
| Instance | A Helm release. | Its UUID comes from the module's registry path without the major, the instance name and the namespace, so it survives module upgrades, a major bump included. Rendered objects carry it in the `module-instance.opmodel.dev/uuid` label. Objects are named `<instance>-<component>`, the shape of Helm's `<release>-<chart>`. |
| Module path and registry | An OCI chart reference (`oci://…`) or an image reference. | The module path is a CUE import path ending in `@vN`. The exact version is a separate pin in the importing module's `cue.mod/module.cue`. A registry mapping sends path prefixes to registries, such as `opmodel.dev=ghcr.io/open-platform-model`, and the longest matching prefix wins. `opm` reads the mapping from `--registry`, `OPM_REGISTRY` or `registry` in `~/.opm/config.cue`, in that order, then from `CUE_REGISTRY`. |
| Module template | `helm create` and Helm starter charts. | Templates are published modules under `opmodel.dev/templates`: `minimal`, `standard` (the default) and `advanced`. `opm module init <module-path> <template>` fetches one from the registry. `--from` starts from any published module instead. |
| Render (`opm instance build`) | `helm template`. | A render needs a platform. It refuses, with no partial output, when a component matches no transformer or a contract it demands has no transformer on the platform. `--skip-unprovided` is the one exception: it skips, with a warning, only a provider-fulfilled contract nothing on the platform provides. `opm instance build` and `opm instance vet` read the cluster only to find its `Platform`; a missing or unreadable one does not fail them, and `--offline` keeps them off the cluster. |
| Apply (`opm instance apply`) | `helm upgrade --install`. | The CLI uses server-side apply and records the inventory in a `ModuleInstance` resource, so the CRD must be installed (`opm operator install --crds-only`). On the next apply it prunes the objects the new render no longer emits, unless you pass `--no-prune`. It never prunes a Namespace. |
| Inventory | The Helm release Secret (`sh.helm.release.v1.*`). | The inventory is `status.inventory` on the `ModuleInstance` resource. It holds one entry per object, with `group`, `kind`, `namespace`, `name`, `v` (the version) and `component`, and no manifests. Whichever of the CLI or the operator owns the instance writes it. |
| Prune (`spec.prune`) | Flux Kustomization `spec.prune`. | For an instance the operator owns, the operator deletes stale objects, and everything on deletion, only when `spec.prune` is `true`. The field has no default, and the CLI never writes it. The CLI prunes on its own apply unless you pass `--no-prune`. |
| Owner (`spec.owner`) | No direct equivalent. The nearest is a Helm release installed by hand compared with one a Flux HelmRelease manages. | The owner is `cli` or `operator`, and an empty owner means `operator`. For a `cli` instance the operator renders, applies and prunes nothing: it sets the Ready condition to Unknown with reason `ManagedExternally`. The CLI never changes an owner, and no command moves an instance between the two. |
| opm-operator | Flux's helm-controller reconciling a HelmRelease. | The operator fetches the module from the registry by `spec.module.path` and `spec.module.version`, and renders it against the cluster's `Platform`. It cannot use a module that exists only as local files, so `opm instance apply` refuses one for an instance the operator owns. |
| `ModuleInstance` resource | A Flux `HelmRelease`. | Namespaced, short name `mi`. Its spec has `module`, `values`, `prune`, `owner`, `suspend`, `serviceAccountName` and `rollout`. The same kind records the instances the CLI manages. |
| `ModulePackage` resource | A Flux `Kustomization` with a `sourceRef` and a `path`. | It reads `instance.cue` at `spec.path` in a Flux `OCIRepository`, `GitRepository` or `Bucket`, and renders it only when it evaluates to a `#ModuleInstance`; any other kind is refused. Short name `mpkg`. |
| `TransformerRegistration` resource | An `APIService` registering an aggregated API. | A cluster-scoped claim, short name `treg`, that a provider module ships among its rendered objects to add its catalog's transformers to the platform. It is named `<namespace>.<name>` after the instance that ships it. Creating one needs `create` on `transformerregistrations`, which no role the operator ships grants to tenants. The operator refuses a second claim for a catalog or contract that is already provided. |
| Kernel | Helm's Go SDK, embedded in another program. | The kernel acquires, validates and renders. It applies nothing: applying and pruning belong to the CLI and the operator, which embed it. |
